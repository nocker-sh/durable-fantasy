# コードの作り

ディレクトリの役割と依存の向きは `AGENTS.md` の「ディレクトリ構成」で決めてある。この文書は、それらがどうつながって動くかを書く。言葉の意味は [[glossary]]、サーバーの決まりは [[game-system]] にある。

## 操作が流れる順

ブラウザでは `world/game.ts` の Game がゲーム全体を持つ。Game は three.js の場面、キー入力、部屋との接続、プレイヤーのデータを持ち、画面に出すものを一つの値（`world/state.ts`）にまとめる。React の部品（`components/`）は、`components/game/context.tsx` を通してその値を読み、Game のメソッドを呼ぶだけで、ゲームの状態を自分では持たない。セッションの状態と、接続・サーバー通知・会話・生産や装備操作・交流の処理は `world/client/` が受け持つ。各処理は同じ GameSession を参照し、必要な操作だけを渡される。`world/parts/` はキー入力、開いている窓、部屋の先読み、会話の選択肢、出来事の知らせなどを受け持つ。

ブラウザはマップの部屋と WebSocket でつながる。送り合うメッセージの形は `world/protocol.ts` にあり、サーバーは受け取ったメッセージを zod で確かめる。部屋の入口は `routes/map/[mapId].ws.ts` で、メッセージの種類ごとの処理は `world/server/map-room/` にある。

部屋は位置にかかわる確認をする。歩いた道がそのマップの歩けるマスを通っているか、店主や扉に十分近いか、などである。確認が済むと、部屋はそのプレイヤーの Durable Object に規則の実行を頼み、結果を本人に返す。規則そのものは `world/core/` の純粋な関数で、状態とコマンドを受け取り、受け入れて新しい状態と出来事を返すか、理由を付けて断る。同じ関数をブラウザでも使い、押せないボタンを灰色にする。結果を決めるのはいつもサーバーである。

## Durable Objects

Durable Object の入口は `durable-objects/` にあり、どれも Void の規約に従う。プレイヤー一人ごとの `player`、町ごとの `directory` と `nature`、全部の町で一つの `market` と `exchange`、生き物の具合を持つ `wild`、パーティごとの `party` がある。どれをいくつ持つかは世界観と対応させてある（[[world#世界の作りと Durable Objects]]）。マップの部屋は誰もいなくなると何も持たずに閉じ、続けて残すべきものは `player` などほかの Durable Object に置く。

## 定義表

住民、世帯と建物、日課、台詞、店、アイテム、レシピ、マップは TypeScript の定義表にあり、状態は ID だけを持って定義表から引く。住民と町の表は `world/town/`、ルールにかかわる表は `world/core/`、マップは `world/maps/` にある。住民と台詞は世帯単位、建物は地区単位でファイルを分ける。住民の一覧順は焼き出したスプライトの番号に対応するため、定義の置き場所を変えても順は変えない。マップの歩けるマスと住民の立つ場所は、描画の側の地形から `scripts/export-map.ts` で `world/maps/<マップ>.json` に書き出し、サーバーはこの JSON だけで確かめる。場面を組み立てなくてよいようにするためである。地形や建物を変えたら書き出し直す。

## 描画

マップの描画の入口は `world/scene/index.ts` の MapScene で、地形・住民配置・照明・歩行者・入力は `world/scene/runtime/` に分ける。建物・野外・小物・テクスチャはそれぞれ `construction/`・`fields/`・`props/`・`textures/` に、人物の体・服・髪・装備・描画は `figure/` に分ける。描画は `world/scene/` が受け持ち、ゲームに依存しない部品は `lib/graphics/` と `lib/engine/` にある。地面の絵は重いので、いくつかの Web Worker で帯に分けて描き、描いた絵はブラウザの IndexedDB に残して次からはそれを使う。残した絵は描くコードそのものを鍵にしているので、コードを変えれば描き直される。住民の姿はドット絵のスプライトで、`scripts/bake-sprites.ts` で前もって八方向の動きを `public/tmp/sprites/` に焼いておく。この生成物は Git に含めない。焼いていない組み合わせ（プレイヤーの見た目など）は、スプライト用の Worker がその場で描く。`world/scene/anims.json` は生成されたモーションデータであり、実装ファイルと同じ理由では分割しない。灰は物ごとに板を足さず、材質のシェーダーで空を向いた面に積もらせる。

描画は低い性能の機械でも動くことを優先し、設定画面は置かない。動かない物は、材質が同じで、いちばん近い「動く親」（薄くなる家、消える屋台、揺れる木の冠など）が同じもの同士を一つのメッシュにまとめて描く（`lib/graphics/batch.ts`）。物の数も見た目も変えず、GPU に出す命令の数だけを減らす。どれが動く物かは、場面の動きを何度か進めて位置が変わったかで見分ける。影は毎フレームではなく、決まった間隔と太陽が動いたときにだけ描き直し、フレームレートは一定に抑える（間隔と上限は `world/scene/runtime/create.ts`）。

## 開発用の道具

`/dev` のページ（`pages/dev/` と `dev/`）では、定義表を一覧し、住民や物を一つずつ見て、描画を試せる。ゲームの画面には開発用のものを出さず、開発用のパネルは開発中のビルドにだけ出す（[[ui#1. 原則]]）。

`scripts/` のスクリプトは bun で動かす。マップの書き出し、スプライトの焼き込み、屋外のマップと屋内の写真撮り、`/dev` の全ページがはみ出していないかの確認、経済の試算がある。写真を撮るものは開発サーバーを動かした状態で使う。

## テスト

テストは実装と同じディレクトリに `*.test.ts` で置き、`npm test` で動かす。規則のテストは `world/core/` の関数を直接呼ぶ。町の暮らしの整合（寝床の数、日課、通れる道、軒先の物の置き場など）もテストで確かめ、テストにできないものは [[consistency]] のチェックリストで確かめる。`lib/engine/` には、依存の向きと実行時の import に循環がないことを確かめるテストがある。型だけの依存は `import type`・`export type` で明示し、実行時の依存に含めない。
