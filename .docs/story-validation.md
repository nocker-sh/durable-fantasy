# 物語と依頼の自動検証

物語や依頼を変更するときは、開始条件・会話・完了操作・得るもの・繰り返した結果を、本番データと実際の進行処理に対するテストへ反映する。テスト専用の進行規則や台詞を作らない。前提条件と結果を別々に検査し、進行を直接書き換えて到達できたと扱わない。

`vp run test:story` はブラウザなし、単一ワーカーで依頼・会話・親しさ・保存の関連検査を実行する。全体テストにも同じ検査を含む。重い検査は直列で行い、ブラウザ確認は並列実行しない。

`keys-movement.test.ts` は正本の町の歩行可能な格子を局所条件とし、全移動キーを実際のキー受付・経路探索・移動処理へ通す。Ctrl・⌘の押下・解放や文書の非表示でキーによる移動を解除し、歩行キーの解放通知が失われても現在の区間を終えて停止すること、反復通知だけでは再開せず新しい押下で動けることを確認する。表示中の通知では移動を解除せず、キーが保持されていない場合のクリック移動も保つ。`keys.test.ts` は再購読と終了時に文書の購読を残さないことも照合する。差し替えるのはウィンドウ入力と経路の送信先で、描画、実通信、地形の生成、町への到達経路は対象外。

`controllers.test.ts` は取引所の発注・取消・受取を実際のクライアントの要求・返事の照合・プレイヤー状態の反映へ通す。成功・拒否の返事を待つ間の閉鎖、品目変更、同じ品目の開き直し、通常の継続と接続の置換を検査する。切断でも待機を解消し、閉じた掲示板を開き直さず、選択を巻き戻さず、別の接続へ古い処理から読出しを送らない。開いている掲示板だけを現在の品目で再取得し、取引結果の反映と待機解除は本番処理を使う。画面・所持金・接続済み状態は局所条件で、差し替えは通信の配送と表示への出力だけとする。ここでは返事を与えてクライアント側を検査し、サーバー側の約定・資産の精算・保存や町からの到達、実通信と最終画像の保証とは分ける。

`dialogue-resumption.test.ts` は正本の全依頼を日替わり提示から選び、本物の会話開始・ページ送り・受注や引渡しの選択、通信待ちと返事の照合へ通す。受注・完了・報酬と重複拒否はサーバーと共通の `apply` で作り、成功した状態はJSONから実際の読込処理へ戻して返事に使う。成功・拒否それぞれで、会話の継続・閉鎖・同じ相手との話し直し・接続の置換を検査し、古い処理が新しい会話や履歴を上書きしないことを確かめる。受注と引渡しの連打は待機中の会話を閉じず、一つの要求と結果だけを通す。材料・提示日の時計・相手への到着は局所条件で、引渡し用の受注記録も本物の操作で作る。差し替えは時計・通信の配送・表示と既読保存の出力先で、依頼の判定・選択肢・会話とプレイヤーの更新は本番処理を使う。住民の予定に沿った移動・材料集め・クラウドでの永続化・実通信・最終画像は別の検査とする。

## 依頼から表示と保存まで

`errand-playthrough.test.ts` は実行用の依頼定義を無条件で列挙する。本物の日替わり抽選と住民の予定から、その日の期限内に依頼元と受取人に会える場面を選ぶ。初期資材を明示し、受注・引渡しはサーバーと共通の `apply` を通す。親しさや依頼の進行は注入しない。

受注前と期限切れの選択肢、受注後・材料不足・引渡し可能・受取人に対する完了後の会話と選択肢を照合する。その段階の専用台詞が定義されている場合に実際に選ばれ、別段階の台詞は出ないことを確認する。すべての依頼と段階に専用台詞があることは要求しない。配達依頼元の完了後は進行値だけを確認し、専用台詞の選択は対象外。

必要な材料だけを消費し、報酬と親しさが一度だけ増えることを確かめる。相手違い、重複受注、重複引渡し、期限切れでは拒否理由と状態の不変を確認する。

受注後と完了後の状態をJSONにして実際の保存読込処理へ渡し、再開後も同じ会話・選択肢と重複拒否が保たれることを確かめる。追加した依頼を対象から除外して成功にしない。

`errand-resumption.test.ts` は全依頼を実 Player DO の受注・引渡しへ通し、それぞれの書込みを失敗させても保存済みの全記録が変わらないことを確認する。別の Player DO インスタンスへ再起動して再試行し、材料の消費・代金・親しさ・完了記録が一度だけ反映され、受注と引渡しの再送では全記録が変わらないことを検査する。時刻は本番の日替わり抽選から選び、開始材料は局所条件とする。住民への接触や経路はこの保存入口の検査には含めない。

`map-room/errand-resumption.test.ts` は全依頼を、本物の部屋の受付から Player DO の操作と保存へつなぐ。会う日時は `errand-meetings.ts` を既存の進行検査と共用し、日替わり提示と住民の予定から選ぶ。住民のそばには、マップの出現位置からつながる歩行可能なセルを使う。不在の部屋と受注前の報告、材料不足では全保存記録を変えず、受注と報告の保存失敗はその場で再試行する場合と実行オブジェクトを再起動する場合の両方を検査する。確定後に返信だけを失っても、再起動後の報告で材料・報酬・親しさと完了を重ねない。部屋が接続を認めた後、RPC の配送直前に別接続へ引き継ぐ場合と退出する場合も、受注・報告を拒否して全保存記録を保つ。古い要求は再起動後も受け付けない。材料と位置は局所条件で、住民のそばへの移動は Player DO の travel と arrive で接続と入場位置を組み立てる。保存先・時計・クラウドの起動環境と RPC の解決・配送順、返信の出力先だけを差し替え、部屋の在席と距離の確認、依頼・回復・報酬・保存と拒否は本番処理を使う。実際に町を歩く経路、材料入手、会話画面からの要求送信と返事の表示、実通信とクラウドのディスク、最終画像はこの検査の対象外。

`map-room/commission-resumption.test.ts` は職人の依頼を正本から全件列挙し、予定表に沿って職人がいる日時と、出現位置からつながる歩行可能な受付位置を選ぶ。本物の部屋の受付から Player DO の発注・完成待ち・受取・保存へ通し、不在の部屋では断ること、発注と受取の保存失敗から同じ個体でも再起動後でも再試行できること、確定した受取の返事だけを失っても品・品質・作り手・親しさを二度反映しないことを確かめる。受付後、操作の配送直前に別接続へ引き継ぐ場合と退出する場合は、発注・受取を拒否し、再起動後にも古い操作を受け付けない。受取に先立つ本番の読出しは回復と公開番号を正当に保存するので、拒否した操作と書込み失敗の不変性はその読出し後の全保存記録と照合する。同じ時刻の再送では公開番号の一回分の増加だけを許し、進行全体のほかの項目は一致させる。材料・代金・運搬能力と入場位置は局所条件で、保存先・時計・乱数・クラウドの起動環境、RPC の解決と配送順・返信先だけを差し替える。在席・距離・接続の照合、完成時刻・材料と代金・品質・報酬・保存は本番処理を使う。移動と材料の入手経路、依頼画面からの要求送信、実通信とクラウドのディスク、全障害の同時発生や最終画像はこの検査の対象外。

`client/selected-commission.test.ts` は正本の全製作依頼を実 `PlayerActions`・`GameSession`・`RoomClient` と本番の `apply` へつなぐ。画面の受取ボタンは描画時の依頼一覧を渡し、送信前に既存の `sameCommissionOrders` で照合する。材料と運搬力・代金だけを局所的に用意し、本番の発注で同じ職人への二件を作り、実際の完成時刻まで時計を進める。別の受取で先頭が詰まる場合・追加の発注・全件受取を本番の操作で起こし、表示後と通信中のそれぞれで古い選択を拒否すること、拒否で全状態を保ち、進行の出来事を出さないことを確認する。送信前の試行では、誤った要求が出れば通信先の本番コアにも実際に渡し、古い画面が別の品を受け取ってしまう結果を検査する。一覧以外の材料を本番の破棄で変えても正しい選択は受け取り、待機中と受領後の同じ入力で二件目を受け取らない。確定した全状態・公開値・出来事を直接の本物の受取と照合する。時計と通信の配送先・通知先だけを差し替え、保存スキーマでも全準備状態を検証する。取引窓のクリック自体・窓口の距離や営業時間・DO の保存と再送・接続確認は既存の検査とは分け、材料の入手と窓口への移動、全品質・数量・時刻の組合せ、実通信と最終画像はこの追加検査の対象外。

## 検査の境界

`craft-capacity.test.ts` は上限より先のレシピも含む正本の全制作を `apply` へ渡す。材料を使っても枠が空かない満杯の所持品では、拒否して代金・スタミナ・材料・経験値を含む元の状態を変えない。材料の消費で枠が空く場合と、重ねられる完成品の同じ品質・作り手の束にちょうど収まる場合は実際に制作し、数量と支払いを照合する。別の作り手の束に混ぜて枠を補わないことも確認する。運搬量ちょうどで重さが増える制作は拒否し、既に一単位超過していても重さが増えない制作は受けられるという既存の規則を保つ。作り損じは枠不足の拒否とは別の、材料と使用料を払う受理結果として検査する。満杯と重量境界の開始状態は本番の保存読込でも受けられることを確かめる。技能・運搬力・資材と所持枠の配置は局所条件で、入手・育成経路、全品質の組合せ、サーバーでの保存と再送、時間回復・距離や最終画面はこの検査とは分ける。ゲームの判定・品質・出力・所持品処理は差し替えない。

予定から選んだ場所と時刻、持込み材料は明示した初期条件。そこまで歩く経路、採集による材料の入手、実ネットワークと実 Workers のストレージ、全住民の親しさの到達経路、全条件の組み合わせは、この検査だけでは証明しない。

選択肢や台詞の出力検査と、最終的な配置・読みやすさは分ける。出力データだけでは判断できない変更に実画面の確認を使う。


`craft-resumption.test.ts` は正本の全レシピについて、成功・失敗それぞれの実制作を Player DO へ渡し、保存失敗後の再開、材料・代金・スタミナと完成品、同じ要求の再送、内容の変更と古い番号の拒否を検査する。作業場への距離と部屋からの通知は `map-room/craft-resumption.test.ts` で確認する。正本の全レシピを実際に配置された設備へ結び、距離不足では保存・姿勢の通知・抽選を変えず、近くでの保存失敗は未確定のまま再試行できることを確かめる。成功と作り損じの両方で、その後の応答消失から実行オブジェクトを再起動し、同じ要求を異なる抽選値で再送しても、材料・代金・スタミナ・完成品と経験の保存を重ねず、出来事を再通知しないことを照合する。従来のスープによる検査も維持する。拒否済みの要求は後から材料を足しても結果を変えず、新しい番号なら実行できる。再送の応答は別操作後の現在の状態を返し、出来事を再発行しない。技能・運搬力・材料と設備の近くの位置は局所的な開始条件であり、そこまでの移動・育成やブラウザの送信操作を検証したものではない。保存先・時計・乱数・返信障害と RPC の接続先解決だけを差し替え、部屋の距離確認・制作・保存の受理判断と読込・再送の判定は本番処理を使う。
